# 标签归属存储 — 设计取舍

> 状态：**有效**（2026-10-26 定）。若被取代，把这一行改成「> 状态：已被 <新文档> 取代」。
>
> 需求与验收：`docs/CHANGELOG.md` 的 `[0.2.0]`「兼容」段｜用法：[../usage.md](../usage.md) 的「标签与类型」
> 这份文档记的是"为什么不建关联表"——这是最容易被"善意重构"推翻的一个决定。

## 一句话

标签的类型归属存在 **`nodes.tagtypes` 一个 JSON 列**里，**不建 `node_tags` 关联表**；`tags` 仍是逗号串，格式不动。

## 决策清单

| # | 决策 | 选择 | 被否方案 | 为什么 | 代价 |
|---|---|---|---|---|---|
| 1 | 归属存哪 | `nodes.tagtypes` JSON：`{"核心":["类别","阶段"]}` | 关联表 `node_tags(node_id, tag, type)` | 节点是**整图重写**的，JSON 跟着走：复制画布、版本快照、导出全都不用改 | 不能用 SQL 按类型聚合；前端要解析 JSON |
| 2 | `tags` 格式 | 保持逗号串不变 | 改成 JSON 数组 / 加 `类型::名字` 前缀 | 旧页面、旧快照、旧草稿、回滚旧服务端**全都不用动** | 标签名里不能出现逗号 |
| 3 | 老数据怎么读 | **缺键 = 老数据**，回落到 `tag_defs` 老表 | 启动时一次性把所有行改写成显式 | 零迁移、零风险；老库打开后显示与升级前逐像素一致 | 两套语义要长期并存并解释清楚 |
| 4 | 取消类型怎么表示 | 显式写 `[]` | 删掉这个键 | 删键会被"缺键回落"复活成旧类型——用户改了等于没改 | JSON 比"干净"的数据多几个空格级冗余 |
| 5 | `tag_defs` 老表 | 保留，并继续写一份"名字→第一个类型"的投影 | 直接删表 | 回滚旧版服务端时还能显示类型 | 投影**有损**（同词多类型只留第一个），且是遍历顺序决定的 |
| 6 | 类型校验 | 服务端白名单清洗（类型必须在 `tag_types` 里、去重、坏 JSON 归一为空串） | 信任前端 | 防脏载荷与悬空类型；换客户端也不会写坏 | 客户端提交前要拿到最新类型表 |

## 展开：为什么"缺键"和"`[]`"必须区分

这是整套设计里唯一"看着多余、实则必须"的地方。

```
用户把「核心」从「类别」里取消
  → 若写成"没有这个键"：下次打开 → 缺键回落 → 又从 tag_defs 补回"类别" → 用户改了白改
  → 必须写成 "核心": [] → "我明确不要类型了"
```

所以读的时候是三级优先：**有键用键 → 有键且为 `[]` 就按未分类 → 没键才回落老表**。

## 已知欠债

1. **`tag_defs` 是有损投影**：只留第一个类型，回滚旧版时看不到"第二归属"。
2. **没有标签词表**：标签只存在于使用它的节点上，最后一个节点删掉，标签就消失了（目前是有意为之，避免"空标签"堆积）。
3. 按类型做**统计/导出**只能在前端遍历，SQL 侧没有索引可用。

# 文档地图

> 本仓库文档遵循 **单一事实源 + 薄壳**：每件事只写一处，其它地方只放指针。

| 文件 | 回答什么 | 什么时候改 |
|---|---|---|
| [../README.md](../README.md) | 这是什么 / 给谁用 / 凭什么是它 / 快速开始 | 定位或能力变化时（≤150 行） |
| [../AGENTS.md](../AGENTS.md) | 架构、铁律、命令、流程、禁区（**agent 入口**） | 结构或约定变化时 |
| [usage.md](usage.md) | 怎么用：参数、编辑、快捷键、标签、多画布、导出 | 功能用法变化时 |
| [data-model.md](data-model.md) | 表结构、兼容策略、HTTP 接口、体检口径 | 表 / 接口变化时 |
| [auth.md](auth.md) | 账号：**怎么用**（设计取舍不在这里） | 账号用法变化时 |
| [designs/](designs/) | **关键取舍**：选了什么、否掉了什么、代价是什么 | 做结构性决策时新增一篇 |
| [CHANGELOG.md](CHANGELOG.md) | 版本历史（**唯一记录处**） | 每次发布 |
| [../DEPLOY.md](../DEPLOY.md) | 部署、反代、备份迁移 | 部署方式变化时 |
| [../CONTRIBUTING.md](../CONTRIBUTING.md) | 给人看的参与入口（三分钟上手 + 提交前检查） | 流程变化时 |
| [../SECURITY.md](../SECURITY.md) | 威胁模型与漏洞报告方式 | 安全边界变化时 |

### 目录怎么分：按"读者来干什么"，不按"是否常青"

> 常见的误区是按寿命分（一次性 vs 常青）——但除了 `requirements/` 里的任务文档，
> 其余**全都是常青的**，按寿命分不开。真正的依据是**内容类型**：

| 位置 | 回答的问题 | 例子 | 随什么变 |
|---|---|---|---|
| [usage.md](usage.md) · [auth.md](auth.md) | **这个软件怎么点**（操作手册） | "点右上角 → 用户管理 → 新增" | 跟着功能变 |
| [data-model.md](data-model.md) | 表结构 / 接口长什么样（参考） | `users(id,name,pass,role,must_change)` | 跟着实现变 |
| [designs/](designs/) | **为什么这么选、否掉了什么** | "令牌里为什么不装角色" | 几乎不变（决策记录） |
| `guides/`（**暂未建**） | **抛开这个软件，这类活该怎么干**（方法论 / 经验教训） | "一轮归属确认：先定维度 → 列取值 → 逐部门过缺口" | 不随代码变 |
| [requirements/](requirements/) | **这次要做什么** | spec / plan | 一次性，做完进 archive |

**为什么现在没有 `guides/`**：它装的是"方法论"，而本仓库目前只有"产品手册"。空目录只会制造噪音。
**什么时候建**：当你发现某个做法**要重复讲第二遍**、且它**不依赖本软件的版本**（比如"怎么用画布做一轮归属确认"），
就写 `docs/guides/<YYYY-MM-DD>-<名称>.md`，并在上表登记。

## 任务文档（spec / plan）

结构性改动**先写文档再动手**，放在：

```
docs/requirements/
├── specs/<YYYY-MM-DD>-<名称>.md    # 做什么（目标/范围/口径/验收）
├── plans/<YYYY-MM-DD>-<名称>.md    # 怎么做（任务清单/依赖/验证）
└── archive/{specs,plans}/          # 交付或废弃后移入
```

- **spec 与 plan 必须同名同日期**
- 交付完成后移入 `archive/`（保留子目录结构）
- 涉及"多方案权衡 / 结构性取舍"时，先写 `docs/designs/<YYYY-MM-DD>-<名称>.md`

### 规模分级

| 级别 | 判据 | 要不要写文档 |
|---|---|---|
| **L0** | 改文案、一行修复、样式微调 | 不用 |
| **L1** | 新功能、改接口、改表结构、改兼容策略 | **spec + plan** |
| **L2** | 跨模块重构、迁移、需要分阶段验收 | spec + plan + 拆 tickets |

### spec 模板

```md
# <名称> Spec

## 目标 / 背景
## 范围与不做（YAGNI）
## 输入与来源
## 口径与规则
## 产出
## 验收标准
- [ ] …
## 开放问题
```

### plan 模板

```md
# <名称> Plan

**Goal:** 一句话
**方法概述:** 关键取舍
**依赖:** …

## 全局约束
## 任务清单
### Task 1: …
- [ ] Step …
## 验证清单
## 不做的事（YAGNI）
## 验证记录（交付后补：跑了什么、结果如何）
```
